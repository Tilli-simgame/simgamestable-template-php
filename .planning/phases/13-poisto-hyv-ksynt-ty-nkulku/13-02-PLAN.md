<objective>
Muunna kaikki kuusi sisällönpoistokohtaa hard-delete/admin-only-mallista roolihaarautuvaan soft-delete-malliin: mod:n poisto piilottaa sisällön heti JA luo `pending_deletions`-rivin admin-hyväksyntää varten (MOD-06); admin poistaa suoraan ilman hyväksyntää; author poistaa vain oman postauksensa välittömästi (AUTHOR-03). Lisää samalla `is_deleted = 0` -suodatus näiden sivujen omiin listakyselyihin, jotta soft-deletetyt rivit katoavat admin-näkymistä heti.

Purpose: Tämä toteuttaa poisto-käyttäytymisen roolin mukaan (D-04) — vaiheen ydinlogiikka. Ilman tätä mod-poistot menisivät edelleen suoraan läpi.
Output: Kuusi muokattua poisto-käsittelijää roolihaaroineen ja soft-delete-suodatuksineen.
</objective>

    - public/admin/posts.php rivit 39-46 (IDOR defense-in-depth: `SELECT author_id FROM posts WHERE id` → `requireOwnResourceOrAdmin()` — sama malli post_delete.php:hen)
    - public/src/includes/helpers.php rivit 78-116 (`requireOwnResourceOrAdmin()`, `requireRole()`, `currentRole()`)

  <action>
    `horse_delete.php`: Laajenna `requireRole('admin')` → `requireRole('admin', 'mod')`. Säilytä olemassa oleva POST-tarkistus, CSRF-tarkistus, id-validointi ja `UPDATE horses SET is_deleted = 1, deleted_at = NOW() WHERE id = :id AND is_deleted = 0` sellaisenaan. Lisää UPDATE:n jälkeen ehto: jos `currentRole() === 'mod'`, kutsu `insertPendingDeletion('horse', $id, (int)$_SESSION['admin_id'])`. Admin ei saa pending-riviä (D-04). Säilytä redirect `horses.php?deleted=1`.

    `post_delete.php`: Laajenna `requireRole('admin')` → `requireRole('admin', 'mod', 'author')`. Säilytä POST- ja CSRF-tarkistukset. Muuta id-validointi niin että id ≤ 0 → redirect `posts.php`. Hae postauksen omistaja: `SELECT author_id FROM posts WHERE id = :id`; jos riviä ei ole → redirect `posts.php`. Kutsu `requireOwnResourceOrAdmin((int)$ownerRow['author_id'])` (IDOR-esto — author läpäisee vain omalle postaukselle, admin/mod ohittavat). Korvaa hard-delete `DELETE FROM posts` soft-deletella: `UPDATE posts SET is_deleted = 1, deleted_at = NOW() WHERE id = :id AND is_deleted = 0`. UPDATE:n jälkeen: jos `currentRole() === 'mod'`, kutsu `insertPendingDeletion('post', $id, (int)$_SESSION['admin_id'])`. Admin ja author-oman-postauksen-poisto eivät saa pending-riviä (D-04, AUTHOR-03). Säilytä redirect `posts.php?deleted=1`.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| selain→delete-käsittelijä | Epäluotettu POST (id, csrf_token) ylittää tähän |
| author→post_delete.php | Author saattaa yrittää poistaa toisen omistaman postauksen (IDOR) |
| mod→delete-käsittelijä | Mod:n poiston on luotava pending-rivi, ei suoraa lopullista poistoa |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-13-05 | Elevation of Privilege | post_delete.php (author IDOR) | high | mitigate | `requireOwnResourceOrAdmin()` omistajuustarkistus ennen soft-deletea, identiteetti sessiosta |
| T-13-06 | Spoofing | CSRF kaikilla delete-POST-käsittelijöillä | high | mitigate | `validate_csrf_token()` säilytetään jokaisessa käsittelijässä; ei-POST → redirect |
| T-13-07 | Elevation of Privilege | mod ohittaa hyväksynnän suoralla poistolla | high | mitigate | Mod-haara EI tee lopullista poistoa; luo pending-rivin, admin hyväksyy erikseen (Plan 03) |
| T-13-08 | Tampering | tuplasoft-delete / tuplapending | low | mitigate | `WHERE is_deleted = 0` -guard + insertPendingDeletion()-dedup (Plan 01) |

Ei paketinhallinta-asennuksia — toimitusketju-uhkaa (T-13-SC) ei sovelleta.
</threat_model>
