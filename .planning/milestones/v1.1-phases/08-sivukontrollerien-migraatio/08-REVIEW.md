# Phase 08: Code Review Report

**Reviewed:** 2026-07-04T00:00:00Z
**Depth:** standard
**Files Reviewed:** 7
**Status:** issues_found

## Summary

All seven controllers were reviewed for the migration from HTML-rendering pages to
data-only controllers that delegate rendering via `resolveThemePath()`. SQL access is
consistently parameterized (no injection vectors found — even the interpolated
`$contactCols`/`$contactJoins` fragments in `hevonen.php` are static strings, not
user input). Output escaping is correctly deferred to theme templates, and the
controllers only hand off raw fetched rows, which is consistent with the stated design.

The main defect is a **control-flow inconsistency introduced by the migration**: four
of the seven controllers (`hevonen.php`, `hevoset.php`, `index.php`, `kasvatus.php`)
correctly guard the final `resolveThemePath('pages/X.php')` call with a `=== false`
check and return a 404, but the other three (`ajankohtaista.php`, `postaus.php`,
`yhteystiedot.php`) removed that guard and `require` the return value unconditionally.
Since `resolveThemePath()` is documented to return `string|false`, this is a real,
reachable crash path — not a hypothetical one, given that themes are actively being
created/deleted in this same phase (see `oma-talli`/`testitema` theme churn in git
history). The remaining findings are minor edge-case bugs and duplication left over
from collapsing seven near-identical files.

## Critical Issues

### CR-01: Unchecked `resolveThemePath()` return value causes unhandled fatal error instead of 404

**File:** `public/pages/ajankohtaista.php:56`, `public/pages/postaus.php:69`, `public/pages/yhteystiedot.php:27`

**Issue:** These three controllers end with:
```php
require resolveThemePath('pages/ajankohtaista.php');
```
`resolveThemePath()` has the signature `string|false` and returns `false` when the
requested template does not exist in either the active theme or the `default`
fallback theme (see `public/src/includes/theme.php:92-117`). `require false` is not
a no-op in PHP — `false` is coerced to the empty string, and PHP emits:
```
Warning: require(): Filename cannot be empty in ...
Fatal error: require(): Failed opening required '' ...
```
This is an *uncaught* fatal error, not a controlled 404. It produces a blank
page or (if `display_errors` is on, which is common in the Docker dev environment
referenced in project memory) leaks the absolute server path in the trace.

Contrast this with the other four migrated controllers, which correctly guard the
same call:
```php
// hevonen.php:137-142, hevoset.php:33-38, index.php:37-42, kasvatus.php:29-34
$_themePage = resolveThemePath('pages/hevonen.php');
if ($_themePage === false) {
    http_response_code(404);
    exit;
}
require $_themePage;
```
The three files under `CR-01` had this exact guard available as a pattern
elsewhere in the same migration and simply didn't apply it — this is a regression
in defensive coverage, not a pre-existing issue. Given that this phase is actively
adding/removing theme directories (`oma-talli`, deleted `testitema`), a theme that
is missing one of these three page templates (while still being non-default, so it
skips the top-of-file override branch) will crash the entire route.

**Fix:**
```php
// ajankohtaista.php, postaus.php, yhteystiedot.php — apply the same guard
$_themePage = resolveThemePath('pages/ajankohtaista.php'); // adjust filename per page
if ($_themePage === false) {
    http_response_code(404);
    exit;
}
require $_themePage;
```
Consider extracting this into a single helper (see `WR-02`) so the guard cannot be
dropped again in future migrations.

## Warnings

### WR-01: `!empty($_GET['slug'])` silently rejects the literal slug `"0"`

**File:** `public/pages/hevonen.php:23`, `public/pages/postaus.php:16`

**Issue:** PHP's `empty()` treats the string `"0"` as empty (`empty('0') === true`).
Slugs are generated by `slugify()` (see `public/src/includes/helpers.php:24-30`),
which lower-cases and strips non-alphanumeric characters — a horse/post whose
slugified name reduces to `"0"` (e.g., a name that strips down to just a digit, or a
manually-set slug of `"0"`) can never be looked up via `?slug=0`, because the
condition falls through to the `elseif (!empty($_GET['id']))` branch and then to
the `404` branch if no `id` is also supplied. This is a genuine (if narrow) reachable
bug, not just a style nit — it silently breaks lookup for a valid data value.

**Fix:**
```php
if (isset($_GET['slug']) && $_GET['slug'] !== '') {
    $slug = preg_replace('/[^a-z0-9\-]/', '', strtolower(trim($_GET['slug'])));
    // ...
} elseif (isset($_GET['id']) && $_GET['id'] !== '') {
    // ...
}
```

### WR-02: Theme-override boilerplate duplicated verbatim across all 7 controllers

**File:** `public/pages/ajankohtaista.php:6-11`, `public/pages/hevonen.php:6-11`, `public/pages/hevoset.php:6-11`, `public/pages/index.php:6-11`, `public/pages/kasvatus.php:6-11`, `public/pages/postaus.php:6-11`, `public/pages/yhteystiedot.php:6-11`

**Issue:** Every controller repeats the identical 6-line block (only the file name
argument changes):
```php
$_vt_themeFile = resolveThemePath('X.php');
if ($_vt_themeFile !== false
    && !str_starts_with(THEME_PATH, THEMES_ROOT . 'default' . DIRECTORY_SEPARATOR)) {
    require $_vt_themeFile;
    exit;
}
```
This is exactly the kind of duplicated-helper-logic risk the migration should have
consolidated. It already has drifted once — the final `resolveThemePath('pages/X.php')`
guard at the bottom of each file (see `CR-01`) is present in 4/7 files and missing
in 3/7, which is precisely the kind of inconsistency that copy-pasted boilerplate
invites.

**Fix:** Extract both the top override check and the bottom render-or-404 step into
shared helpers in `helpers.php`, e.g.:
```php
function maybeRenderThemeOverride(string $file): void {
    $themeFile = resolveThemePath($file);
    if ($themeFile !== false
        && !str_starts_with(THEME_PATH, THEMES_ROOT . 'default' . DIRECTORY_SEPARATOR)) {
        require $themeFile;
        exit;
    }
}

function renderThemePageOrFail(string $file): void {
    $themePage = resolveThemePath($file);
    if ($themePage === false) {
        http_response_code(404);
        exit;
    }
    require $themePage;
}
```
Then each controller becomes `maybeRenderThemeOverride('ajankohtaista.php');` ...
`renderThemePageOrFail('pages/ajankohtaista.php');`, eliminating the possibility of
one file forgetting the guard.

### WR-03: `$s['stable_name']` accessed without null-coalescing, inconsistent with sibling fields

**File:** `public/pages/yhteystiedot.php:21`

**Issue:**
```php
$stable_name = $s['stable_name'] !== '' ? $s['stable_name'] : SITE_NAME;
$nickname    = $s['owner_nickname']  ?? '';
$vrl_id      = $s['owner_vrl_id']    ?? '';
```
Every other setting read from `$s` uses `??` to guard against a missing array key,
but `stable_name` does not. If the `settings` table has no `stable_name` row, `$s`
will not contain that key, and `$s['stable_name']` raises a PHP warning
("Undefined array key") and evaluates to `null`. `null !== ''` is `true`, so
`$stable_name` ends up `null` instead of falling back to `SITE_NAME` as intended —
the opposite of the fallback behavior the line is trying to implement.

**Fix:**
```php
$stable_name = ($s['stable_name'] ?? '') !== '' ? $s['stable_name'] : SITE_NAME;
```

## Info

### IN-01: Archive-building query and loop duplicated verbatim

**File:** `public/pages/ajankohtaista.php:45-54`, `public/pages/postaus.php:55-67`

**Issue:** Both files run the identical `GROUP BY YEAR(created_at), MONTH(created_at)`
query and build the identical nested `$archive[$yr][$mo] = $cnt` structure. This is
copy-pasted business logic that will drift if one file's archive semantics change
without the other being updated.

**Fix:** Extract into a shared helper, e.g. `getPostsArchive(PDO $db): array` in
`helpers.php`, and call it from both controllers.

### IN-02: Slug-sanitization logic duplicated verbatim

**File:** `public/pages/hevonen.php:24`, `public/pages/postaus.php:17`

**Issue:**
```php
$slug = preg_replace('/[^a-z0-9\-]/', '', strtolower(trim($_GET['slug'])));
```
appears identically in both files. Minor duplication, but if the slug charset rule
ever changes (e.g., to allow underscores), both call sites must be updated in sync.

**Fix:** Extract to `function sanitizeSlugParam(string $raw): string` in `helpers.php`.

### IN-03: `array_filter()` result not reindexed before handoff to template

**File:** `public/pages/kasvatus.php:26-27`

**Issue:**
```php
$expected = array_filter($allFoals, fn($f) => $f['status'] === 'expected');
$born     = array_filter($allFoals, fn($f) => $f['status'] === 'born');
```
`array_filter()` preserves the original (non-sequential) keys. Depending on how the
theme template consumes `$expected`/`$born` (e.g., `$expected[0]`, `json_encode()`,
or any index-based access), a gap in keys could cause unexpected behavior — a plain
`foreach` is safe, but this is an implicit assumption not enforced here.

**Fix:**
```php
$expected = array_values(array_filter($allFoals, fn($f) => $f['status'] === 'expected'));
$born     = array_values(array_filter($allFoals, fn($f) => $f['status'] === 'born'));
```

### IN-04: Unnecessary `prepare()`/`execute()` for parameterless queries

**File:** `public/pages/hevoset.php:14-30`, `public/pages/kasvatus.php:14-23`

**Issue:** Both queries have no bound parameters (`$stmt->execute();` with no
arguments), yet use `$db->prepare()` + `execute()` instead of the simpler
`$db->query()` used elsewhere in the same files (e.g., `index.php:16`,
`ajankohtaista.php:36-40`). Not incorrect, just an inconsistent pattern that adds
noise relative to the more direct `query()` call used for the same purpose
elsewhere in the codebase.

**Fix:** Use `$db->query(...)` for queries with no parameters, reserving
`prepare()`/`execute()` for parameterized statements, matching the style already
used in `index.php` and `ajankohtaista.php`.
